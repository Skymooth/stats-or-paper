# 研究中的七类失败模式（自查清单）

来源：Lu et al., *Towards end-to-end automation of AI research*, Nature 651:914–919, 2026（doi:10.1038/s41586-026-10265-5，CC-BY 4.0）。该文的系统完成了从选题到成稿的全流程，这七类是作者对自己产出的复盘。

**为什么必须看**：这七种失败**看起来都像合格的工作**。一条编造的实验结果，读起来和真的一样；一次走捷径的结果，读起来和真泛化一样；一段虚构的方法描述，读起来和忠实记录一样。

**适用范围**：任何用生成式工具参与研究流程的工作——写代码、跑实验、查文献、起草文稿。不是你用了 AI 才适用，而是你用了 AI 之后，这些失败变得**更便宜、更隐蔽**。

---

## 使用方式

开题与定稿前逐条给结论，四选一：

| 结论 | 含义 |
|---|---|
| **CLEAR** | 有证据证明不适用（记一句证据） |
| **SUSPECTED** | 某条检测问题答得可疑 → 必须写进风险并在正文处理 |
| **INSUFFICIENT** | 需要你的实验日志才能判断 → 先去把日志找出来 |
| **N/A** | 确实不适用（例如纯理论论文的第 1、3 条） |

**阻断规则**：任何一条 SUSPECTED，或第 1 / 3 / 5 / 6 条为 INSUFFICIENT → 不许进定稿。

---

## Mode 1：实现 bug 通过自动自审

**是什么**：代码有 bug（差一、变量写错、静默除零、类型强转、参数标错），产出的数字**看起来合理但科学上错**。跑一遍、看一眼、没发现明显异常，就写进论文。

**检测问题**：

- 论文里每一个数字，有没有对应的脚本运行记录？退出码是 0 吗？有没有被忽略的 warning？
- 有没有**可疑地圆整**的数字（正好 0.5、正好 2 倍、方差正好为 0）？圆整是常量泄漏的典型信号。
- 误差棒 / 置信区间在不同条件间**真的在变**吗，还是意外地一模一样？
- 每个报告的量，是从原始表的哪个子集、经过什么过滤条件算出来的？输入路径与阈值写清了吗？

---

## Mode 2：编造引用

**是什么**：文献不存在；或引错了（年份、期刊、作者、DOI）；或把某个发现安到不该安的文章上。

**检测问题**：

- 每条引用能否 30 秒内点开？
- 打开后，它**真的支持你这句话**吗（不只是题目像）？
- 它是正式版还是预印本？

**流程**：见 `evidence.md` §二的程序化核验四步。

---

## Mode 3：编造实验结果

**是什么**：论文写"我们观察到 12% 的提升"，但**没有任何一次运行产出过 12%**——可能是算错了平均、可能引用了崩溃那次的数、也可能是为了让故事成立而编的。

**检测问题**：

- 每个"提升 X% / 降低 Y%"的 claim，原始数字在哪？
- 论文里的表格，能不能对应到一个保存的 CSV / 日志文件？
- 论文写"跑了 N 个种子"，实际有几个运行目录？
- 报告的样本量是"数据集有多大"还是"我实际算了多少"？（这两件事经常被混为一谈，且混错的后果是把单点估计当成了稳健结论。）

---

## Mode 4：走捷径

**是什么**：结果是真的，但方法靠**虚假特征**拿到的。经典案例：色彩偏置的数据集上准确率 99%，靠的是读背景色，不是认目标。

**检测问题**：

- 有没有一个受控消融，能排除最明显的捷径特征？
- 论文的"消融"是真的在拆你声称的机制，还是只在调超参？
- 基线够强吗——赢它是否必须靠你的机制，而不是靠更多算力 / 更多调用 / 更多数据？
- 提升是否只出现在"你的预算更高"的设定里？

---

## Mode 5：把 bug 包装成新发现

**是什么**：出现了意外结果，其实是 bug，但写作阶段把它写成了"我们发现 X 在 Y 条件下出人意料"。**这种论文比没 bug 的版本更"有意思"**，也更容易被接收，因此更危险。

**检测问题**：

- 初稿里有没有 "surprisingly / unexpectedly / counterintuitively / 出乎意料"？每出现一次，能否引一篇**预测了相反结果**的文献？如果没有任何文献预测相反 → 这个"意外"可能不是发现，是 bug。
- 这个意外是第一次跑就出现，还是调试很多轮后才出现？**首跑意外 = 高风险。**
- 有没有在全新环境、新数据、新随机种子下复现过这个意外？

**这是最隐蔽的一条**，因为它同时满足"有趣"和"错误"。

---

## Mode 6：方法描述造假

**是什么**：方法节描述的实验、超参、数据、流程，**不是实际跑的**。按"合理的实验应该长什么样"去写，越写越偏离实情。

**检测问题**：

- 方法节里每个数字（学习率、批大小、轮数、数据量、划分比例、温度）是否出现在真实的运行配置里？
- 方法节描述了某个预处理步骤，你能在代码里指出它吗？
- 方法节用了过去时，但那一步其实没跑过？
- 文中声明"所有调用都固定了某参数"，你能证明每一次都设了吗（包括失败重试的路径）？

---

## Mode 7：早期阶段的框架锁定

**是什么**：在早期（问题框定、方法选择、超参方向）做了一个错误承诺，后续阶段**结构上退不回来**。最后论文执行得很好，但答的是错问题。

**检测问题**：

- 如果现在回到选题阶段，你会改研究问题或方法吗？
- 讨论节里有没有"事后看""我们后来意识到"？这是框架锁定的信号。
- 论文的贡献，是被这个框架**解释**的，还是**尽管有这个框架**才成立的？
- 有没有哪条结论其实在为一个你早已放弃的假设辩护？

**处理方式**：把"为什么放弃原框架"写进引言或附录。**它本身就是可信度。**

## 七条速查表

| # | 模式 | 一句话检测 | 你的结论 |
|---|---|---|---|
| 1 | bug 过自审 | 每个数字有日志吗？圆整可疑吗？ | |
| 2 | 编引用 | 每条能点开且真的支持吗？ | |
| 3 | 编结果 | 表格能对上 CSV 吗？样本量是实际算的吗？ | |
| 4 | 走捷径 | 有排除捷径特征的消融吗？同预算比过吗？ | |
| 5 | bug 当发现 | 每个"意外"有文献预测相反吗？ | |
| 6 | 方法造假 | 方法节每个数字在配置里吗？ | |
| 7 | 框架锁定 | 回到起点会改问题吗？ | |

## 一条元规则

这七条的共同点是：**它们都不会自己暴露**。

所以唯一的防法是**把证据留在手边**——日志、CSV、运行配置、检索记录。写"局限"节时你会发现：那些能随手拿出证据的地方写得最轻松，那些拿不出的地方，就是最该删的 claim。
